# Release checklist

Work down the list for every release. Tick items in the release's GitHub issue or PR.

## 1. Before you start

- [ ] `main` is green in GitHub Actions (coding standards, build, Plugin Check, every PHP × WordPress test job).
- [ ] docs/FOLLOWUPS.md has nothing marked as blocking this release.
- [ ] security@airworthywp.com works: send it a test email and check it arrives.

## 2. Update the facts that go stale

- [ ] **PHP support dates.** Compare `Targets::SECURITY_UNTIL` in `plugin/src/Targets.php` with https://www.php.net/supported-versions.php. Update any changed date, add a new PHP version when one is released (also add it to `Targets::ALL`, `docs/ACCURACY.md` and the readme), and set `Targets::TABLE_CHECKED` to today. The CI check "Support table checked within the last 13 months" fails when this has been forgotten for over a year.
- [ ] **New PHP version?** Check that the pinned PHPCompatibility version knows it. If not, update it (see "Bundled libraries" below) and re-run the fixtures and the top-30 comparison in docs/ACCURACY.md.
- [ ] **WordPress.** Set `Tested up to` in `plugin/readme.txt` to the current major WordPress version, after the tests pass on it.
- [ ] **Bundled libraries.** Check for security releases of PHP_CodeSniffer, PHPCompatibility, PHPCSUtils and Action Scheduler (GitHub advisories, Patchstack, WPScan). To update, edit the pins in `plugin/composer.json` and run `bin/build.sh --update`. Update the version numbers in the readme's "Bundled libraries" section. The SBOM updates itself.

## 3. Version number

Set the new version (semantic versioning: x.y.z) in all three places:

- [ ] `plugin/airworthy.php`: the `Version:` header.
- [ ] `plugin/airworthy.php`: `define( 'AIRWORTHY_VERSION', … )`.
- [ ] `plugin/readme.txt`: `Stable tag:`.

Then:

- [ ] Add a changelog entry to `plugin/readme.txt` (and an Upgrade Notice for anything users must know). For security fixes, write "Security fix" and the severity, without exploit details.
- [ ] Regenerate the translation template: `wp i18n make-pot plugin plugin/languages/airworthy.pot --exclude=vendor,languages --headers='{"Report-Msgid-Bugs-To":"https://wordpress.org/support/plugin/airworthy"}'` and check there are no new "translators:" warnings.

## Test builds (before a release)

Zips for real-site testing are release candidates: `RC=3 bin/build.sh` numbers the build `X.Y.Z-rc.3` (the source keeps `X.Y.Z`). Count up with every test zip you hand out, so sites can tell builds apart and browsers reload the admin screen. rc.1 to rc.9 of 1.0.0 went out on 27 Sep 2026 (next: rc.10). Name handed-out zips with the version: airworthy-1.0.0-rc.N.zip.

## 4. Build and check

- [ ] `bin/build.sh` (release build: no `DEV_BUILD`). It fails if the lock file, the PHP-Scoper checksum or the scoping patches are wrong.
- [ ] `vendor/bin/phpcs`: 0 errors, 0 warnings.
- [ ] Plugin Check on the built plugin: `wp plugin check airworthy` → 0 errors. Remaining warnings must be the known ones in the section below.
- [ ] Clean-site install: on a fresh WordPress site with no other plugins, install `dist/airworthy.zip` through Plugins > Add New > Upload, activate, run a scan from Tools > Airworthy, check the results screen and the CSV export, then delete the plugin and check nothing is left (`tests/after-uninstall.php`).
- [ ] `docs/sbom.cdx.json` was regenerated by the build and lists the right versions.

## 5. WordPress.org submission (first release only)

- [ ] Report the two reversed `implode()` bugs to Essential Addons for Elementor and UpdraftPlus first, and wait for fixes (or a reasonable time). Screenshots 2–4 show both plugins (4 with the file and line) and go on the WordPress.org listing, so recapture them without those plugins or wait. The development repo (damien-cork-boi/airworthy) names both bugs and stays private.
- [ ] github.com/DigitalKind/airworthy (the public source repo, made by `bin/export-public.sh`) is public and up to date: the readme's "Source code and build" section links to it.

## 6. Publish

- [ ] Update the public source repo: `bin/export-public.sh` (copies an allowlist into `../airworthy-public` and refuses if anything private is in it), review, commit "Airworthy X.Y.Z", tag and push there.
- [ ] Commit, tag `vX.Y.Z` and push the tag. Create a GitHub release with the zip and `sbom.cdx.json` attached.
- [ ] Deploy to WordPress.org SVN: copy `build/airworthy/` to `trunk/`, copy trunk to `tags/X.Y.Z`, and put `assets/icon.svg`, `assets/icon-*.png`, `assets/banner-*.png` and the screenshots from `assets/screenshots/` in the SVN `assets/` folder (brand images are rendered from `assets/source/` with `npm run brand` in `site/`). Commit.
- [ ] Check the WordPress.org page, and that a test site sees the update and updates cleanly.

## 7. After release

- [ ] Watch the support forum and security@airworthywp.com for a week.
- [ ] Move anything learned into docs/FOLLOWUPS.md.

## Known Plugin Check warnings

Plugin Check 2.1.0 on 1.0.0: **0 errors, 0 warnings** after the per-line ignores below.

- `PluginCheck.Security.DirectDB.UnescapedDBParameter` (49 places): our own table names (`{$wpdb->base_prefix}airworthy_scans`, `_components`, `_issues`, fixed strings from `Installer::tables()`, never user input) are put into the SQL string directly. Every value is a `prepare()` placeholder. Each line has a `phpcs:ignore` with the reason "Own table." A cleaner option, possible since our minimum is WordPress 6.5, is the `%i` identifier placeholder (WordPress 6.2+); see docs/FOLLOWUPS.md.
- `vendor/` is skipped by Plugin Check. It contains the scoped scan engine and Action Scheduler, which are third-party libraries (Action Scheduler is the same library WooCommerce ships). Their own coding style (for example Action Scheduler's `action-scheduler` text domain) is not ours to change.
