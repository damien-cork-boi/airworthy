# Release checklist

Work down the list for every release. Tick items in the release's GitHub issue or PR.

## 1. Before you start

- [ ] `main` is green in GitHub Actions (coding standards, build, Plugin Check, every PHP × WordPress test job).
- [ ] docs/FOLLOWUPS.md has nothing marked as blocking this release.
- [x] security@airworthywp.com works: send it a test email and check it arrives (tested 29 Sep 2026).

## 2. Update the facts that go stale

- [ ] **PHP support dates.** Compare `Targets::SECURITY_UNTIL` in `plugin/src/Targets.php` with https://www.php.net/supported-versions.php. Update any changed date, add a new PHP version when one is released (also add it to `Targets::ALL`, `docs/ACCURACY.md` and the readme), and set `Targets::TABLE_CHECKED` to today. The CI check "Support table checked within the last 13 months" fails when this has been forgotten for over a year.
- [ ] **New PHP version?** Check that the pinned PHPCompatibility version knows it. If not, update it (see "Bundled libraries" below) and re-run the fixtures and the top-30 comparison in docs/ACCURACY.md.
- [ ] **WordPress.** Set `Tested up to` in `plugin/readme.txt` to the current major WordPress version, after the tests pass on it.
- [ ] **Bundled libraries.** Check for security releases of PHP_CodeSniffer, PHPCompatibility, PHPCSUtils and Action Scheduler (GitHub advisories, Patchstack, WPScan). To update, edit the pins in `plugin/composer.json` and run `bin/build.sh --update`. Update the version numbers in the readme's "Bundled libraries" section. The SBOM updates itself.

## 3. Version number

Set the new version (semantic versioning: x.y.z) in all three places:

- [ ] `plugin/airworthy.php`: the `Version:` header.
- [ ] `plugin/airworthy.php`: `define( 'AIRWORTHY_VERSION', … )`.
- [ ] `plugin/readme.txt`: `Stable tag:`.

Then:

- [ ] Add a changelog entry to `plugin/readme.txt` (and an Upgrade Notice for anything users must know). For security fixes, write "Security fix" and the severity, without exploit details.
- [ ] Regenerate the translation template: `wp i18n make-pot plugin plugin/languages/airworthy.pot --exclude=vendor,languages --headers='{"Report-Msgid-Bugs-To":"https://wordpress.org/support/plugin/airworthy"}'` and check there are no new "translators:" warnings.

## Test builds (before a release)

Zips for real-site testing are release candidates: `RC=3 bin/build.sh` numbers the build `X.Y.Z-rc.3` (the source keeps `X.Y.Z`). Count up with every test zip you hand out, so sites can tell builds apart and browsers reload the admin screen. rc.1 to rc.22 of 1.0.0 went out by 28 Sep 2026 (next: rc.23); test builds set the readme Stable tag to the rc version too. Name handed-out zips with the version: airworthy-1.0.0-rc.N.zip.

## 4. Build and check

- [ ] `bin/build.sh` (release build: no `DEV_BUILD`). It fails if the lock file, the PHP-Scoper checksum or the scoping patches are wrong.
- [ ] `vendor/bin/phpcs`: 0 errors, 0 warnings.
- [ ] Plugin Check on the built plugin: `wp plugin check airworthy` → 0 errors. Remaining warnings must be the known ones in the section below.
- [ ] Clean-site install: on a fresh WordPress site with no other plugins, install `dist/airworthy.zip` through Plugins > Add New > Upload, activate, run a scan from Tools > Airworthy, check the results screen and the CSV export, then delete the plugin and check nothing is left (`tests/after-uninstall.php`).
- [ ] `docs/sbom.cdx.json` was regenerated by the build and lists the right versions.

## 7. After release

- [ ] Watch the support forum and security@airworthywp.com for a week.
- [ ] Move anything learned into docs/FOLLOWUPS.md.

## 8. Keeping up (the yearly checklist)

Why this section exists: WP Engine's PHP Compatibility Checker (200,000 sites, added 2016) was discontinued with no more releases, not even security fixes. Its rating fell to 2.7/5 with half its reviews at 1 star, and the most common complaints were "abandoned" and "doesn't support newer PHP" (it stopped at PHP 8.0). Its scanner wasn't the problem; falling behind was. Staying current is part of the product.

**Every new PHP version (released each year in late November; the next is due late 2026):**
- [ ] Check that the scan engine (PHPCompatibility, PHPCSUtils, PHP_CodeSniffer) has rules for the new version. If it doesn't yet, say so plainly in the readme FAQ rather than stay silent.
- [ ] Add the version to `Targets::ALL` and its support dates to `Targets` (from php.net/supported-versions.php), and update `TABLE_CHECKED`.
- [ ] Add the new target to `tests/expected-verdicts.json` and the CI checks; run the accuracy set from docs/ACCURACY.md against it.
- [ ] Update the "PHP 8.0 to 8.x" wording: readme (description, changelog, FAQ), site hero line and Pro teaser (site/src/pages/index.astro), and the screenshots if the target picker changed.
- [ ] Release within a few weeks of the PHP release, and say so in the changelog ("Adds PHP 8.x").
- [ ] Add the new PHP version to the CI matrix once setup-php and WordPress support it.

**Every WordPress major release (about three a year):**
- [ ] Run the full tests against it (CI's "latest" job does this automatically after release; check it passed).
- [ ] Bump "Tested up to" in the readme. If nothing else changed, this is a readme-only commit to SVN `trunk/` and the current `tags/X.Y.Z/`, no new version needed. WordPress.org warns visitors about plugins not tested with the last three major releases, and that warning costs installs.

**Twice a year (January and July):**
- [ ] Check the bundled libraries (Action Scheduler, PHP_CodeSniffer, PHPCompatibility, PHPCSUtils) for new releases and security fixes; update, rebuild, check the SBOM and the readme's library list (the build fails if they disagree).
- [ ] Re-run Plugin Check on the latest version: its rules change.
- [ ] Re-check the PHP support dates in `Targets` against php.net.

**Always:**
- [ ] Answer every support-forum thread within two working days, even if only to say it's being looked at. Resolved threads show on the plugin page.
- [ ] Keep security@airworthywp.com monitored (SECURITY.md promises it).
- [ ] The scan never depends on a server of ours. PHP Compatibility Checker moved its scanning to a remote service (Tide) and died with it. Pro may use our servers for alerts and licences, never for the scan itself.

## Known Plugin Check warnings

Plugin Check 2.1.0 on 1.0.0: **0 errors, 0 warnings**.

- SQL (changed 30 Sep 2026 for the WordPress.org review): every query goes through `$wpdb->prepare()` with a fixed SQL string. Table names use the `%i` identifier placeholder (WordPress 6.2+), never string interpolation; lists use a fixed-length `IN (%s,%s,%s,%s)` (see `Rest\Controller::filter_values()`); issues are saved with `$wpdb->insert()`. Only `CREATE TABLE` for `dbDelta()` still names our tables directly, as `dbDelta()` requires. Keep it this way: the reviewers reject SQL built from variables, and `FIND_IN_SET` doesn't work on SQLite (WordPress Playground).
- `vendor/` is skipped by Plugin Check. It contains the scoped scan engine and Action Scheduler, which are third-party libraries (Action Scheduler is the same library WooCommerce ships). Their own coding style (for example Action Scheduler's `action-scheduler` text domain) is not ours to change.
